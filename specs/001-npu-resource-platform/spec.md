# Feature Specification: 昇腾 NPU 资源管理平台

**Feature Branch**: `001-npu-resource-platform`  
**Created**: 2026-01-12  
**Status**: Draft  
**Input**: User description: "本项目旨在构建一个**计算资源使用管理平台**，用于纳管研发团队内部的 10+ 台昇腾 (Ascend) NPU 服务器集群。 当前痛点为资源使用混乱、冲突频发且状态不透明。需要提供一个透明的服务器资源平台, 支持用户可以在平台查看当前有哪些服务器(哪些卡)可用, 预约对应的服务/卡的使用权限。同时提供报表,监控等能力透明化所有人的服务器资源使用情况。 包含但不局限于以下功能: 1. **SSH 动态“硬”门禁 (Dynamic Access Control)** - **诉求**：修改目标服务器的 `authorized_keys` 必须是**即时且自动**的。预约生效那一秒公钥写入，预约结束那一秒公钥删除。 - _验收_：无预约状态下，`ssh user@ip` 必须直接报错 `Permission denied`。 2. **控制面与数据面解耦 (Fail-Safe Architecture)** - **诉求**：管理平台挂了（Web宕机），**不能**踢掉正在跑任务的 SSH 连接。 - _验收_：重启 ServerSentinel 服务期间，已连接的用户终端不应断开。 3. **用户白名单与公钥强绑定 (Identity Binding)** - **诉求**：不接受陌生注册。只有管理员录入账号的用户才能登录，且用户**必须**上传 SSH 公钥才能发起预约。 - _验收_：未上传公钥的用户，预约按钮应置灰不可用。 4. **互斥的双模式调度 (Dual-Mode Exclusion)** - **诉求**： - 模式A（整机）：锁住全机，禁止其他人申请该机任何卡。 - 模式B（拼车）：锁住 Card-0，其他人可申请 Card-1。 - _验收_：Server-1 被人以“整机模式”锁定时，另一用户申请 Server-1 的 Card-0 必须提示冲突失败。 5. **严格的时间窗防撞 (Time-Slot Collision Detection)** - **诉求**：在时间轴上，任何新预约段不能与已存在的预约段有 1秒钟 的重叠。 - _验收_：已有预约 14:00-15:00，申请 14:59-16:00 必须被拒绝。 6. **环境变量注入指引 (Environment Guidance)** - **诉求**：针对“拼车模式”，系统需生成“使用指南”，明确告知用户需设置的环境变量。 - _验收_：预约成功弹窗需显示：`export ASCEND_VISIBLE_DEVICES=0`（引导用户只用申请的卡）。 7. **NPU 拓扑自动发现 (Topology Auto-Discovery)** - **诉求**：输入 IP/账号，系统自动识别是 910B 还是 310，是 8卡 还是 2卡。 - _验收_：新加一台机器，数据库自动填充其 Chip ID 和 HBM 大小，无需人工填表。 8. **昇腾指标实时映射 (Ascend Native Metrics)** - **诉求**：必须解析 `npu-smi` 输出，展示 AI Core 利用率、HBM 显存、温度。 - _验收_：仪表盘上的数值需每 <30秒 刷新一次，且准确反映当前负载。 9. **状态“红绿灯”可视化 (Traffic Light UI)** - **诉求**：首页必须是矩阵视图。 - _验收_：一眼能区分：绿色（空闲）、红色（他人占用）、蓝色（自己占用）、灰色（离线/故障）。 10. **管理员“上帝之手” (Admin Force Release)** - **诉求**：管理员拥有一键强制结束预约的权限，用于回收僵尸资源。 - _验收_：点击“强制释放”后，占用者的 SSH 权限即刻失效，资源回归资源池。 11. **僵尸任务检测 (Idle/Zombie Detection)** - **诉求**：解决“占着茅坑不拉屎”或“人走了程序还在跑”。 - _验收_：UI 需高亮显示“无预约但 NPU 高负载”或“有预约但 NPU 零负载”的异常状态。 12. **全链路审计日志 (Full Audit Trail)** - **诉求**：所有操作留痕，用于事后扯皮或成本核算。 - _验收_：能导出一份报表，显示“用户A 在 上周五 占用了 Server-3 的 0号卡 共计 4小时”。"

- Q: SSH 登录账号策略 → A: 每位平台用户映射到独立系统账号（账号名与 Web 登录一致）

- Q: 审计日志保留期限 → A: 30 天

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 预约与准入控制 (Priority: P1)

用户查看服务器与卡的可用状态，提交预约（整机或拼车），并在预约生效时获得
对应 SSH 访问权限。

**Why this priority**: 解决资源冲突与不可用问题，是平台核心价值。

**Independent Test**: 用户可在不依赖其他故事的情况下完成查询、预约与准入校验。

**Acceptance Scenarios**:

1. **Given** 用户在白名单且已上传 SSH 公钥，**When** 选择服务器与时间窗并提交，
   **Then** 预约成功且在生效秒级启用访问权限。
2. **Given** 同一服务器已有整机模式预约，**When** 其他用户申请任意卡，
   **Then** 系统提示冲突并拒绝预约。
3. **Given** 已有预约 14:00-15:00，**When** 申请 14:59-16:00，
   **Then** 系统拒绝该申请。
4. **Given** 用户未上传 SSH 公钥，**When** 打开预约页面，
   **Then** 预约按钮不可用且提示需先上传公钥。

---

### User Story 2 - 资源状态与监控可视化 (Priority: P2)

用户在首页矩阵视图中查看资源状态与占用情况，实时掌握负载与异常。

**Why this priority**: 提升透明度与协作效率，减少资源争用与盲用。

**Independent Test**: 用户可独立完成状态查看与异常识别，无需管理员操作。

**Acceptance Scenarios**:

1. **Given** 服务器在线且无人占用，**When** 用户打开首页矩阵，
   **Then** 显示为绿色空闲状态。
2. **Given** 用户本人在占用某卡，**When** 查看矩阵，
   **Then** 该卡显示为蓝色自己占用。
3. **Given** 无预约但负载持续异常，**When** 查看监控，
   **Then** 系统高亮提示异常占用。

---

### User Story 3 - 管理员治理与审计 (Priority: P3)

管理员管理用户白名单、服务器入库与强制释放，并导出使用报表。

**Why this priority**: 保障权限可控与成本核算，支持异常回收。

**Independent Test**: 管理员可独立完成新增服务器、强制释放与审计导出。

**Acceptance Scenarios**:

1. **Given** 新增服务器已录入 IP/账号，**When** 执行入库，
   **Then** 自动补全服务器型号、卡数与关键硬件信息。
2. **Given** 资源处于预约占用，**When** 管理员点击强制释放，
   **Then** 预约终止且访问权限立即失效。
3. **Given** 管理员选择上周时间窗，**When** 导出报表，
   **Then** 报表包含用户、服务器、卡号与占用时长。

---

### Edge Cases

- 预约结束与开始相差 1 秒时，是否被视为冲突。
- 管理平台短暂不可用时，已建立的 SSH 连接不被中断。
- 服务器离线或故障时，预约应被阻止并明确提示。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供服务器与卡的可用性视图，包含空闲、他人占用、自己占用与离线状态。
- **FR-002**: 系统 MUST 支持整机与拼车两种互斥调度模式，并对冲突申请进行阻断。
- **FR-003**: 系统 MUST 在预约生效时秒级启用访问权限，在预约结束时秒级撤销权限。
- **FR-004**: 无预约状态下，用户 MUST 无法通过 SSH 访问目标服务器。
- **FR-005**: 只有管理员录入的白名单用户 MUST 可以登录系统并发起预约。
- **FR-006**: 用户未上传 SSH 公钥时，系统 MUST 禁止其发起预约。
- **FR-006a**: 用户的 SSH 登录账号 MUST 与 Web 登录账号保持一致。
- **FR-016**: 系统 MUST 限制预约最早开始时间不超过当前时间 3 天。
- **FR-007**: 系统 MUST 拒绝与现有预约存在任何 1 秒重叠的时间窗申请。
- **FR-008**: 拼车模式预约成功时，系统 MUST 提示用户所需环境变量示例指引。
- **FR-009**: 系统 MUST 自动识别新服务器的型号与卡规格并填充资产信息。
- **FR-010**: 系统 MUST 展示 NPU 关键指标（AI Core 利用率、HBM 显存、温度）。
- **FR-011**: 系统 MUST 提供仪表盘，指标刷新频率不低于每 30 秒一次。
- **FR-012**: 系统 MUST 高亮显示“无预约但高负载”与“有预约但零负载”的异常状态。
- **FR-013**: 管理员 MUST 可一键强制释放预约并立即回收访问权限。
- **FR-014**: 系统 MUST 记录所有关键操作并支持导出使用报表。
- **FR-015**: 管理平台短暂停机时，已建立的 SSH 会话 MUST 保持不中断。
- **FR-017**: 审计日志 MUST 至少保留 30 天。

### Non-Functional Requirements *(mandatory)*

- **NFR-001**: 用户界面与交互 MUST 与现有团队习惯保持一致，并保持状态颜色语义稳定。
- **NFR-002**: 预约启停权限与监控刷新 MUST 满足秒级与 30 秒级时效要求，
  并提供可验证的测量方式。
- **NFR-003**: 测试范围 MUST 覆盖预约冲突、权限启停、异常检测与审计导出等关键路径。

### Key Entities *(include if feature involves data)*

- **User**: 账号ID、SSH 登录账号（与 Web 登录一致）、白名单状态、SSH 公钥、所属团队。
- **Server**: 服务器标识、在线状态、型号、卡数量与规格摘要。
- **NPU Card**: 卡编号、所属服务器、占用状态、当前预约关联。
- **Reservation**: 用户、资源、模式、时间窗、状态。
- **Metric Snapshot**: 指标时间点、负载与温度等关键数据。
- **Audit Log**: 操作主体、时间、对象、结果与备注。

## Assumptions

- 平台面向内部研发团队使用，管理员负责维护用户白名单。
- 资源规模约 10-50 台服务器，核心使用场景为预约与透明化展示。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 的预约在生效与结束时 1 秒内完成权限启停验证。
- **SC-002**: 冲突预约（含 1 秒重叠）拒绝率达到 100%，无冲突漏放行。
- **SC-003**: 首页矩阵状态在 30 秒内刷新并准确反映当前占用与离线状态。
- **SC-004**: 90% 的用户可在 1 分钟内找到可用资源并完成预约。
- **SC-005**: 管理员可在 1 分钟内完成强制释放并恢复资源可用状态。
- **SC-006**: 审计报表可准确统计用户占用时长，误差不超过 1 分钟。
